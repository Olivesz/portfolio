freeflow, in depth

How a key tap becomes typed words on a Mac with no cloud: a growing audio buffer, a model pass every 350 ms, and one rule for when a word is safe to type.

The page runs the same rules over those passes and checks they type exactly what the log says before any picture draws.

01 / 05the situation

Words wherever the cursor is

  1. fig 2Retype each guess, or wait for two
  2. fig 3Seconds each pass would re-read

Dictation that works in any app has one job. You talk, and the words are typed into whatever app has focus: a mail draft, a chat box, a code editor.

freeflow does that on a Mac, with Whisper running on-device through whisper.cpp. No account, no cloud, nothing to pay.

The words should show up while you talk, not after you stop. That is where it gets hard. Whisper only transcribes finished clips. To get words while you talk, the app runs it again every 350 ms on everything captured so far. Each run is a pass, and a later pass often changes words an earlier one got wrong.

Text already typed into another app can’t be quietly edited. Retyping gets the sentence right in the end, but wrong words flash on screen first, and every correction is a burst of backspaces sent into someone else’s app.

There’s a second cost. To revise its guesses, the model has to hear the speech again, and re-reading everything said so far on every pass gets slower the longer you talk.

02 / 05the idea

The rules

  1. fig 4The Mac app’s loop

A few rules handle both problems.

Read the recent audio again every 350 ms, but type a word only once two passes in a row agree on it. Never take a word back. And once enough typed audio piles up, restart the window just before the last typed word, keeping some typed audio for context.

The rest of the page builds this loop one stage at a time, in the order the audio meets them. The Mac app is the one described. The Python engine it was ported from runs the same fixtures in its own tests.

One pass is a guess. Two passes agreeing is a fact.

step 01 · sound in

One growing buffer

The microphone delivers audio at whatever rate the hardware uses. whisper.cpp wants 16000 samples a second, one channel, as floating-point numbers. So every block from the mic is resampled to 16 kHz mono float on arrival and appended to one buffer that only grows.

The loop that runs the model never touches the microphone. It takes a snapshot of the buffer when it needs one.

step 02 · the tick

Gates before every pass

A loop wakes every 350 ms, copies the buffer from the window’s start, and decides whether the model should see it at all.

The gates come first, because Whisper does not stay quiet on silence. It fills silence with phrases like “thank you”.

step 03 · the model

Words with times

whisper.cpp runs the base.en model with greedy decoding and is told to end a segment after every word. So each word comes back with its own start and end time. Greedy is deliberate: beam search crashed whisper.cpp mid-dictation, and a test fails if it comes back.

Those times count from the window’s start, so the window’s offset is added to each start and end. whisper.cpp sometimes times a word past the end of the audio, so times are clamped to the window. Tokens that aren’t speech, like [BLANK_AUDIO], a sound in parentheses or a lone full stop, are dropped as non-speech. Whisper learned them from subtitles.

step 04 · agreement

Type only what two passes agree on

This is the rule the whole app rests on, called LocalAgreement-2. Each pass is compared with the last pass, word by word from the front, ignoring case and spaces.

Words that match are committed and typed. The first mismatch stops the comparison, and everything from there on waits for the next pass.

step 05 · no repeats

Never type a word twice

Every pass re-reads audio whose words are already typed, so those words come back, and whisper.cpp re-times words by up to a second from one pass to the next. So the cut between typed and new words is found by text: the longest run of the last four typed words that the pass repeats, taking the one nearest in time.

Only when the pass repeats none of them does a time rule apply: keep words that start after the last typed word ends, less 0.1 s. Until the fix that added the text cut (commit 262c910), that time rule was the only one.

step 06 · trimming

Trim the window

Once more than 3.0 seconds of typed audio sits in the window, the window is trimmed from the last committed word’s start: it restarts 1.5 seconds before it. The model keeps a little context and never re-reads the rest. It cuts from the word’s start, not its end, because whisper.cpp often stretches a word’s end toward the end of the window.

The staircase becomes a sawtooth.

step 07 · typing

Typing into the focused app

Words are typed as keyboard events. Each event carries a Unicode string of up to 20 characters, so the text arrives intact in any app that accepts typing. This needs the Accessibility permission.

Backspace is kept for one thing, a spoken command, and “scratch that” can only erase what the current dictation typed.

step 08 · stopping

Stopping cleanly

Silence ends it in either mode. After a 400 ms grace, every quiet tick adds its length to a silence clock, and speech resets it. At 1,500 ms it stops, so the fifth quiet tick in a row ends it. In hold mode, letting go of the key ends it sooner.

Either way, the stop only signals the loop to finish. The loop finishes its turn, cuts the quiet off the tail, and runs a final flush that types whatever was left in the tail.

04 / 05what broke

Dropped words

  1. fig 13The benchmark, before and after

Words went missing mid-sentence. A phrase spoken clearly never appeared, and the words after it did.

The repo’s benchmark measures it. It replays 41 public clips through the app’s own streamer, decodes the same audio whole and offline with the same model, and scores both against the reference. The coyote reading is not among its clips. The fix and the window were chosen on 20 speakers and a separate reference clip; 20 more were held out and first scored after the fix was committed.

The old rule kept a new word only if it started after the last typed word ended. whisper.cpp re-times words by up to a second between passes and stretches the last word of a pass toward the window’s end, so new words fell behind the line and were thrown away. The pass logs show it.

The Mac app now finds the cut by text, trims from the last typed word’s start at 3.0 seconds, keeps 1.5, and decodes greedily.

05 / 05results

What is tested, and what CI checks

  1. fig 14Tests, the gate and its control

The streaming rules live in FreeflowCore, a Swift library with no model and no UI, so they can be tested anywhere.

55 Swift tests and 36 Python tests passed on CI at the pinned commit. Both suites run the same fixtures, each a sequence of decoder passes and the words that must be typed after each, and two are taken from real pass logs. CI also builds the release app and replays the benchmark’s gate clips with the real model, and fails if streaming loses more than 2 points of word error against offline, or if the benchmark’s reference clip loses a word. A control run with a broken window has to fail too, and it does.

The ideas fit on one card: copy the buffer every 350 ms, type only what two passes agree on, find the cut by text, never take a word back, and keep the window short.

Every figure on this page is traced to a line listed below. Figures read from the pass logs are computed by the page from the logs’ rows, which are copied into it; the rules are re-run over them first, and nothing draws unless they type exactly what each log says.

Not shown: other models or languages, since the benchmark runs whisper.cpp base.en, an English-only model; other kinds of speech, since its 41 clips are public read speech; and an idle machine, since the lag was timed with other work running.
