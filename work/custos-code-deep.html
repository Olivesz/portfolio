01 · the situation

What it did, and what it said

A coding agent works through tool calls: it edits files, runs commands, reads output. When it stops, it writes a report for the person who asked.

The harness that runs the agent already writes down every tool call. The report is prose the agent writes about itself. Nothing reads the two side by side.

A study of real coding-agent sessions counted how often the agent’s own account of its work was the thing that went wrong.

These are shares of episodes already flagged as gone wrong, so the rate of false reports per session is lower, and not known.

The hard part is that both sides are text. The log is long and noisy. The report is short and confident. A reader can’t tell which sentence in the report is a claim, which log line would settle it, or what to do when the log simply doesn’t say.

The agent already kept the evidence. The work is reading it against what the agent said.

02 · the idea

Read the report against the log

Record every tool call somewhere the agent can’t write. When it stops, cut its report into claims and check each one against that record with a fixed rule.

In auto mode, a claim the record contradicts goes back to the agent before it is allowed to stop.

The agent can say anything. The verdict only listens to the log.

03 · the build

Seven parts, in order

Each part below feeds the next: a recorder, a chain that makes the record tamper-evident, a splitter, the rules, the ladder of verdicts, a limited role for a model, and the loop back to the agent.

step 01 · recorder

A recorder the agent can’t write to

The harness runs a hook before each tool call, one after it, and one when the agent stops. The agent never calls them. After each call the hook appends two rows to a per-session log: the call, and its full result.

The result keeps up to 4,096 bytes, plus a fingerprint of the whole output. Two flags are set right there: piped if the command filtered its own output, truncated if it ran past the cap.

The exit-code file was a fix. The first version printed the exit code into the output itself, and that output went back to the agent. An agent that has seen the marker once can print it later and fake a passing run. So the marker moved somewhere the agent never looks.

The recorder also fails open. If the checker can’t start, every hook exits cleanly and says so. A checker that can’t run is not evidence about the agent, and an early version that turned “checker missing” into “block” would have stopped every turn of a broken install.

step 02 · hash chain

Chain every row to the one before

Each row is written out in one fixed form: keys sorted, no spaces. Its fingerprint is a hash of the previous row’s fingerprint followed by that text. So each fingerprint depends on every row before it.

When the agent stops, its rows are chained and the last fingerprint is printed on the receipt. Edit the stored log afterwards and it can no longer reach that fingerprint. This guards the file after the fact. It is not what keeps the agent out; the hooks are.

To check a log, recompute every fingerprint from the top. The first one that doesn’t match is where the record changed. The repo defines that check; the shipped hooks don’t run it yet.

One thing happens before any row is stored: keys, tokens, private keys, credentials in URLs and KEY=… assignments are replaced, so the record never holds them.

step 03 · claims

Cut the report into claims

The report is cut at sentence ends, new lines, bullets, and joins like “, and ran …” or “, the suite is green”.

Pieces that aren’t a claim about the agent’s own finished work are dropped: questions, plans, offers, other people’s work, pending items, and task titles. What’s left gets a type from the first pattern it matches, plus the files and counts named in the same piece.

With a model key, a per-sentence classifier takes the lead and these patterns become the fallback. The model answers with a sentence number, never with text, so it can’t paraphrase a claim into being.

step 04 · test rule

One rule per claim: the test rule

There are 15 claim types, and 13 have a fixed rule. The test rule shows the pattern they all follow: find the evidence, check it can be read, then compare.

It takes the latest test-runner call in the log. If there isn’t one, the claim is unwitnessed. If the output was filtered, it’s unrecorded. A failure, an empty run, a non-zero exit, or a count the run can’t support makes it contradicted. A clean run that fits, or an unparsed run that exited 0, confirms it.

The count check is narrow on purpose. “Added 12 tests” is about writing tests, not running them, and accusing it would be exactly the false accusation the tool exists to prevent. A missed catch costs one catch. A false accusation costs the tool its credibility.

Claims about files follow the same shape with two witnesses: a write in the log, and the working tree. A file merely being there confirms nothing.

step 05 · ladder

A ladder, and five verdicts

Every claim climbs a ladder until some tier can settle it, and the verdict records which tier spoke. The low tiers are rules. A re-run and a model sit higher, and are used only when the rules can’t decide.

A missing record is never read as a lie. Unrecorded and unwitnessed are the checker reporting the limits of its own evidence, and neither one blocks. Measured over 648 real claims, unrecorded was 21.0% and unwitnessed 28.9%: gating on them would hold half of every report open.

step 06 · model

The model may only agree

With a model key, a reviewer can look at what the rules left open. It may move a claim from unwitnessed to confirmed, citing log rows. It may not accuse on its own.

When the model says contradicted, the claim’s own rule checks again. If the rule agrees, the rule’s tier and citations stand. If not, the model’s view is kept as advice, marked unrecorded, and it never blocks.

The reason is measured. Run the same 18 real sessions through the model twice, and 22.8% of its verdicts flip. So the model never blocks on its own.

step 07 · nudge

Block the stop, send the nudge

In auto mode, the stop hook answers a contradicted claim with a block and a reason. The reason cites the log rows and names the command to run. The nudge is a fixed template: 0 LLM tokens, as the receipt prints it.

A claim clears only on evidence newer than the nudge. Saying the same thing in other words gets the same rule, the same log and the same answer.

04 · what broke

False accusations, and a nudge that taught a lie

An audit aimed at the one verdict that can hurt someone: contradicted. It ran over 93 real sessions, each with a report and at least 3 tool calls.

The fix had three parts. Paths now match whole, with their leading “/”, “~/” or dot. Task titles are no longer claims. And a missing file may only support an accusation when the checker could really have seen it.

Measure the stage where the product can hurt someone, not the stage that’s easiest to label.

The second failure was quieter. A quiet test run prints only its last line. The parser wanted the opening banner, so it didn’t recognise the run, and the rule fell back to the exit code. The exit code was 0, so a report claiming 81 tests when 86 ran was confirmed. The checker’s own advice had been to run the tests quietly.

05 · results

A checker that has to earn its silence

A scoreboard drives the real installed hooks, before-call, after-call and stop, through 10 scenarios whose truth is known by construction. It uses a real git repo, real commands and real output, with no API key and no model, so a score means the same thing on every run.

  • 10/10scoreboard scenarios9/10 and 8/10 with either fix turned off
  • 7%of real claims answered8 of 121 claims answered, 113 abstained

Breaking copies of the checker on purpose started with an earlier embarrassment: a checker that did nothing at all passed 9 of 15 of the relation tests of the time. Tests that can’t tell a working checker from an empty one don’t test it.
