01 / 05the situation

Every thread starts blank

  1. fig 2Typed again in every thread
  2. fig 3Closeness as an angle

A chat model keeps nothing once a conversation ends.

Projects, preferences and background get typed again in every new thread, and nothing typed on one site reaches the other.

Fixing that from outside is hard in two ways. inf-mem has to cut into two sites it does not own, and picking the right few lines out of many needs meaning, not keywords.

The fix needs one way to say which stored line is relevant to a new prompt.

The search here works by meaning, not by matching words. A small model turns each text into 384 numbers. Texts about the same thing end up pointing the same way, and the cosine of the angle between them is the score: 1 for the same direction, 0 for unrelated.

02 / 05the idea

Two moments around every message

The idea is one memory store on the machine, outside every conversation, placed in the path of each message twice.

Before the prompt leaves, the store offers what is relevant. After the reply arrives, it keeps what is new, with help from Groq, a hosted API that runs open models. The same store serves both sites. The opening figure plays the whole round trip.

Read before sending, write after replying, and show the user what goes out.

Each step follows the same message one hop further: from the key press, through the store and the panel, to the chat site, and back as a new memory.

step 01 · holding the prompt

Stand in the way of the send

On chatgpt.com, chat.openai.com and claude.ai, a content script listens on the input box.

Enter (without Shift) and the send button are cancelled, and the text is read out. The page’s script cannot reach localhost itself, so the extension’s service worker posts it to the backend on port 7842. If the worker answers with an error, or no memory passes the gate, the script puts the text back and sends it itself, so the site gets it as typed: no memory, and no lost message.

step 02 · the store

384 numbers per memory

The backend embeds text with BAAI/bge-small-en-v1.5 through fastembed, which runs on ONNX Runtime, so there is no PyTorch and no GPU. The model downloads once, about 130 MB.

Each memory is then one row of a single SQLite file, memories.db: its text, type, importance, counters and its 384 numbers. On start the vectors are loaded into a matrix held in memory for search, with the IDs kept in matrix order. A write touches only its own row.

A prompt goes through the same model, but only to be compared. It is never stored.

step 03 · the first gate

Under 0.61, never offered

The prompt is embedded with the model’s query instruction, then compared with every stored row by cosine, in one pass. Anything under 0.61 is dropped here, before its importance is even looked at.

The gate used to be 0.35, picked by hand. On held-out questions from LoCoMo, a public long-conversation benchmark, that let memories into 100% of off-topic prompts. 0.61, chosen on the other half of the benchmark, cuts that to 4.4%, while recall@5, the share of a question’s evidence found in the 5 memories returned, stays at 0.571 against 0.575 with no gate.

step 04 · ranking

similarity × (1 + importance / 10)

Closeness alone does not set the order. Each surviving memory’s similarity is multiplied by one plus a tenth of its importance, so importance can nearly double a score.

The five best go back to the browser, and each one returned counts one more access.

step 05 · the review panel

Nothing reaches the chat site without a click

Before anything reaches the chat site, a panel slides in with the memories that would go with the prompt. Sending with memory, skipping, or compressing is one click; closing the panel sends nothing.

Compression is off by default. When it is on, Groq rewrites the prompt shorter before the panel opens, and the panel previews the first 150 characters.

step 06 · injection

A plain-text block above the prompt

Approved memories become a plain-text block above the prompt, one line per memory, each marked with its type.

The content script clears the site’s input box, inserts the full text the way typing would, waits 50 ms for the page to catch up, and clicks the site’s send button, or presses Enter when there is none. From here the memories are part of the prompt, and the chat site receives them like any other text.

step 07 · learning from the reply

The Groq call that is always on

Once the reply has finished streaming and its text has stayed the same for 600 ms, the content script passes the prompt and that reply to the worker, once, and the worker posts them to /extract without waiting.

CI checks that on copies of both sites’ pages: one extraction per finished reply. On the live sites, ChatGPT’s composer was checked on 2026-10-13; its reply markup, and claude.ai, are not checked yet.

The backend sends both to Groq’s llama-3.1-8b-instant with fixed instructions: pick out facts, projects, preferences and episodes worth keeping, score each from 1 to 10, and answer with a JSON list, or an empty one. This is the Groq call that is always on; compression is the other, and it is off by default. Without a Groq key the backend refuses it, and nothing new is learned, while /retrieve keeps working.

step 08 · the second gate

At 0.98 or above, the same memory

Each candidate is embedded on the machine and scored against every stored memory in one pass. Only the closest counts. At 0.98 or above it is the same memory: the candidate replaces it if its importance is higher or its text longer, and is skipped otherwise. Anything else is stored as a new memory, under a new ID.

The gate used to be 0.85. On 180 hand-labelled pairs, no cosine threshold that merged anything was right 90% of the time, and 39% of the merges the old gate made joined two different facts. A paraphrase and a different fact score alike, so only near-verbatim restatements merge now.

step 09 · what crosses

What stays, what leaves

Put together, a message leaves the machine for two places: the chat site and Groq. The chat site was always going to get the prompt; it now also gets the memories approved in the panel. Groq gets the prompt and the finished reply for extraction, once per reply, and the prompt alone for compression when that is on.

Storage, embedding, both gates and the ranking run on the machine. The extension’s own settings live in Chrome’s synced storage, which Chrome copies to the user’s Google account when sync is on.

04 / 05what broke

The ID file

  1. fig 13The ID file across two starts

The bug lived between two runs, in the store’s first version.

Vectors and IDs were saved as two NumPy files that must line up row for row. Before the fix, the ID list was saved as a pickled object array. Pickle is Python’s format for arbitrary objects, which NumPy refuses to load unless allowed, because loading it can run code. The store loads both files with pickle turned off, so the ID file could not come back.

During a session the IDs sit in memory, so every add and search inside one run worked. On the next start the backend builds the store, the load fails, and the error stops the backend; the extension then sends every prompt without memory.

The fix saved the IDs as plain strings, with pickle off on both sides. The lesson is in the test. A store that is only opened once can never show this bug, so the test writes a memory, opens a second store on the same folder, and checks that the memory and a 1 × 384 matrix come back.

The store has since moved to SQLite, with each vector in its memory’s row, and an old pair of .npy files is migrated into the database once. The test that opens the store twice is still there.

A bug that only shows on the second start needs a test that starts twice.

05 / 05results

What is measured, and what is checked

  1. fig 14The test tiers, job by job

Retrieval is measured on held-out data, speed on two machines, and every push runs all five test tiers.

On LoCoMo the gate was chosen on five conversations and measured on the other five, 776 questions.

Through the full HTTP stack, with the real model and store and Groq stubbed out, /retrieve at 10,000 memories takes 5 ms at the median and 7 ms at p95 on an Apple M5, and 15 / 19 ms on the CI runner. /extract stays flat as the store grows: 8 ms at 1,000 memories and 9 ms at 10,000 on the M5. CI fails if /extract at 10k takes more than twice as long as at 1k; on the run for c6579f9 it took 1.17 times as long.

Not proven: the live Groq model (every tier mocks or fakes it); on the live sites only ChatGPT’s composer has been checked.
